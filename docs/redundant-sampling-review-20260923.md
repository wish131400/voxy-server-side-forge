# 地形、底边、结构与植被重复计算审查（2026-09-23）

审查对象是游戏实际调用的预测 LOD 路径；所有局部性能数值都不是整游戏 FPS、首次加载耗时或显存改善的估计。此轮源码同时同步到 NeoForge 1.21.1 和 Forge 1.20.1；没有改动存储格式、预测精度、版本号或 JAR 命名。

## 已减少的工作

- `PredictionVegetation.generate` 中无 `BiomeFilter` 的特征原来每个特征都会扫描原点地形列的所有垂直段，重新查询各段生物群系，再检查该特征是否存在。现在每个装饰任务、每种地表模式（精确或展示）仅计算一次可用生物群系列；后续特征仍按原顺序逐一检查原本的 `BiomeGenerationSettings.hasFeature`。缓存仅在一次任务内存活，地形编辑不会改变噪声生物群系或不可变的列垂直段。若该区块没有无过滤特征，不创建这份列表。缓存雪层修复任务沿用原路径。
- `PredictionSurfaceStructures.place` 原来在每个装饰阶段都扫描所有可能结构集合并遍历其结构以筛选阶段。现在在构造世界生成上下文时保持原集合顺序，预建每个阶段的集合列表；进入无结构的阶段无需扫描集合和可能的候选位置。实际候选落点、`start` 缓存、结构随机种子、排序与放置顺序保持原样。

未测量真实整合包里无过滤特征数量、结构集合数量和 FPS，因此不声称以上改动有固定百分比收益；其计算量上限分别是一次装饰任务中同模式的生物群系足迹扫描从 *特征数* 次变为 1 次，以及结构集合阶段筛选从 *装饰阶段数* 次变为构造时 1 次。对带标准 `BiomeFilter` 的原版植被，上述第一项不执行，收益可以是 0。

## 未接入的候选与保留的正确性工作

- 原生 `World::decoration_indices` 原本对邻近生物群系做大范围扫描，但 Java 生成路径使用 `RustVegetationStage.place` 逐特征下发，没有调用这个函数。后续清理已删除它及未使用的 `decorate_step`、JNI/Java 声明和旧整步回滚测试；逐特征事务与测试保留。删除不会减少现有游戏运行时的计算量。
- 原生 `decoration_points` 在查询前为诊断统计持两个缓存锁检查命中，随后实际地表查询会再查缓存。这确实重复了少量映射查询；目前没有证据它比地形和特征执行更重，不为此改变诊断或缓存并发语义。
- 有状态图完整列精确回退会在某些附加生物群系查询里重复建立 scratch。使用 `cache_2d` 包裹垂直梯度的隔离版本，与原实现各取五轮交替测试；`batch8_step1`、`batch8_step4`、`tile66_step1` 的中位数分别为 249.9→267.2 ms、787.3→806.5 ms、958.3→940.4 ms，输出 TSV 逐字节一致。差别为 -6.9%、-2.4%、+1.9%，不构成可重复的明确收益，**不合并该候选**。原始记录见忽略的 `build/redundant-sampling-review-20260923/scratch-reuse-results.csv`。普通非完整列图并不进入这段回调。
- 底边/洞口不能一概跳过四邻居与垂直占地采样，否则悬空山体、薄层和真实孔洞的交接会改变。上一轮同噪声格、至多 8 请求的复用只在可证明安全时启用，隔离对照在 `docs/sampling-reuse-evaluation-20260923.md`；这轮不再改变几何边界。

## 验证

两套版本的 `PredictionVegetationTest` 新增用例覆盖精确/展示分离、缓存复用和缺失特征拒绝；两套完整 Gradle `build` 均通过。新 JAR 由现有构建直接写入各自 `lib`，保留既定文件名。隔离原生测速不是现场性能采样，无法推出实际世界精细化总耗时；需要玩家世界运行时的特征分布与阶段计时才可量化整包收益。
